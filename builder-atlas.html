L'écosystème XRPL est souvent pitché en termes d'architecture — UNL, RPCA, AMM, MPT. Mais quand on est builder, la vraie question est différente : quelle startup je peux lancer dans les 6 prochains mois, en exploitant ce que XRPL fait mieux qu'ailleurs ?

Ce document propose 7 blueprints précis. Chacun part d'un problème de marché concret, identifie pourquoi XRPL est structurellement avantagé pour le résoudre, détaille l'architecture technique exacte, le stack à utiliser, l'économie unitaire, et un plan MVP en 3-4 semaines.

Le but n'est pas de vendre XRPL — c'est de séparer les use cases où le ledger fait gagner de ceux où on ferait mieux d'utiliser autre chose. La matrice de décision en fin de document classe chaque blueprint par couple opportunité × complexité.

BLUEPRINT 01 / 07 Payments · Remittances

RemitFlow — passerelle Philippines ↔ US

Couloir #1 mondial des remittances · 38 milliards $/an · friction structurelle de 6%

PH ↔ US · KSA · UAE

01Problème · Marché

Un travailleur philippin à Riyad envoie 500 USD à sa famille à Cebu. Western Union prend 32 USD de frais (6,4%), le transfert met 1–3 jours, et le destinataire doit se rendre à un point physique pour retirer.

Les acteurs digitaux récents (Wise, Remitly) ont ramené les frais à 2–3% mais restent dépendants de rails bancaires et de partenaires de cash-out locaux qui prennent leur marge.

Pourquoi XRPL plutôt qu'autre chose : finalité 3–5s (vs 1–3 jours bancaires), frais < 0,001$ par transaction, AMM natif XRP/PHP et XRP/USD permet le settlement cross-currency sans intermédiaire FX. Risque clé Le succès dépend des partenaires de cash-out aux Philippines (GCash, PayMaya). Sans eux, le destinataire reste bloqué. Negociation B2B pré-launch obligatoire.

02Architecture XRPL

Payment AMM XLS-30 Path-finding RLUSD Sidechain EVM NFT MPT

L'envoi est une Payment cross-currency unique : USD (issuer Bitstamp) → XRP (via AMM) → PHP (issuer GCash partner). Le pathfinding du ledger trouve automatiquement le meilleur chemin à travers les pools AMM disponibles.

Variantes :

— v1 (KYC light) : custody centralisée chez RemitFlow, l'utilisateur n'a pas de wallet. UX comme Wise. Faster to market.

— v2 (self-custody) : le sender garde son wallet Xaman, signe lui-même. Plus crypto-native, mais friction d'onboarding.

— v3 (RLUSD direct) : évite le swap AMM en utilisant directement RLUSD comme rail stable. Spread quasi nul mais dépend de la liquidité RLUSD↔PHP locale.

Existing Wise · Remitly · WorldRemit · SBI Remit (utilise déjà XRP) · Tranglo (Ripple ODL)

02Architecture XRPL

RLUSD Trustline Payment recurring AMM XLS-30 DID XLS-70 MPT Sidechain EVM

Le user dépose des pesos via une carte ou virement bancaire local. Le backend déclenche : ARS → USD (off-chain via partenaire FX) → RLUSD (mint sur XRPL) → user trustline. Le RLUSD reste détenu sur le compte XRPL du user (custody hybride : multisig user + VaultDAO comme co-signataire de récupération).

Innovation custody : wallet multisig 2-of-3 — clés réparties entre user (mobile), VaultDAO (recovery), backup notarié (bank vault). Le user peut tout retirer seul après cooldown 48h ; en cas de perte mobile, recovery via vidéo-KYC + 2 facteurs.

Yield optionnel : les utilisateurs avancés peuvent activer le mode "yield" qui mobilise leur RLUSD dans le pool AMM RLUSD/USDC (faible volatilité) — rendement passif estimé 3–6% APY, sans contrat smart contract.

02Architecture XRPL

MPT DID XLS-70 Credentials Permissioned Escrow AMM XLS-30 Sidechain EVM

Chaque obligation est un MPT distinct émis par BondBloc (en tant qu'agent émetteur agréé) au nom de la PME. Le MPT inclut : nominal, taux, échéance, fréquence coupons, identifiant ISIN, hash du prospectus. Restrictions natives : seuls les comptes XRPL portant un Credential "investisseur accrédité EU" valide peuvent recevoir/transférer le token.

Cycle de vie automatisé :

— Émission : mint des MPT après collecte 100% de la souscription (escrow conditionnel). Si pas atteint, remboursement automatique.

— Coupons : tx Payment automatique tous les 6 mois vers tous les détenteurs (calcul off-chain, batch on-chain).

— Marché secondaire : pool AMM MPT/RLUSD permet revente sans attendre maturité (avec décote market-driven).

— Maturité : remboursement principal + dernier coupon, burn des MPT.

02Architecture XRPL

02Architecture XRPL

MPT SPV legal wrapper Escrow DID + Credentials AMM secondary Payment batch (rents) NFT title deed

Chaque actif immobilier est wrappé dans un SPV juridique (Free Zone Company à Dubai par exemple). Le SPV émet via PropTok un MPT sur XRPL, où chaque token = 1/N de la propriété économique du SPV. Les loyers nets perçus par le SPV sont convertis en RLUSD et distribués proportionnellement aux holders chaque mois.

Innovation clé : la liquidité secondaire. Concurrent RealT prend 6-8 semaines pour vendre une part. PropTok via AMM permet la vente en 3 secondes (avec spread market-driven). C'est ce qui transforme l'immobilier d'illiquide en tradable.

Title deed NFT (optionnel) : chaque appartement peut aussi avoir un NFT XLS-20 unique qui représente l'asset auprès du registre immobilier dubaïote (DLD pilote ce mécanisme déjà). Le MPT pointe vers ce NFT pour preuve d'authenticité.

02Architecture XRPL

Payment Memo (nonce) RLUSD SetRegularKey SignerListSet EscrowCreate MPT (quota tokens)

Le serveur API renvoie HTTP 402 avec headers x402 (currency, amount, recipient, nonce). L'agent client construit une Payment XRPL (XRP ou RLUSD), la soumet, attend la finalité (~3–5s), puis retry la requête API avec le tx hash dans header X-Payment. Le serveur vérifie on-chain (montant, destinataire, nonce dans memo) et débloque la réponse.

Variantes :

— v1 (per-call XRP) : chaque requête API = 1 Payment XRP avec memo nonce. Verifier valide hash + montant + destinataire on-chain. Le plus simple, idéal pour MVP. Latence ~4s par appel acceptable pour la majorité des use cases agents.

— v2 (sub-account quota) : l'agent reçoit un sub-account via SetRegularKey, avec un cap quotidien via SignerListSet (l'humain peut révoquer instantanément). Verifier accepte des paiements signés par le sub-account jusqu'au quota. Latence quasi-nulle (validation off-chain par signature) mais sécurité moindre — utile pour micropaiements ultra-frequents.

— v3 (escrow workflow) : pour les workflows multi-step (agent qui appelle 5 APIs en cascade), un EscrowCreate bloque le total. Chaque sub-step déclenche un EscrowFinish partiel via crypto-condition. Avantage : pre-commit à un budget total, le user humain peut EscrowCancel avant la deadline.
